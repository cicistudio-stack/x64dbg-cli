# x64dbg-cli milestone gates

Extract used by `src/cli/tests/check_milestones.py`. The full design is not part of the product tree.

### Acceptance criteria

1. **AC-1 Build [M1].** `cmake --build build64 --target cli` produces `bin\x64\x64dbg-cli.exe`. A full `cmake --build build64` still succeeds and still produces `x64dbg.exe`, `x64gui.dll`, `headless.exe`. After the build `bin\x64` contains no `x64dbg-cli.lib` and no `x64dbg-cli.exp` (the target links with `/NOIMPLIB /NOEXP`, 12.1 item 1, like the `exe` target; `headless` does not and leaves `headless.lib/.exp`). The untracked upstream trees (`src/dbg/btparser`, `src/third_party/TitanEngine`, `src/third_party/GleeBug`, `deps`) are not tracked by git (`git ls-files` returns 0 files for them, VERIFIED), so "unmodified" is checked with a SHA-256 manifest: before starting M1 the implementer writes `.agents/tasks/cli/untracked-manifest.sha256` (one `hash  relative path` line per file of those four trees, **no exclusions**: every file found by a recursive listing that includes hidden files, at the time of writing; the build is out of source in `build64`, so none of the four trees receives build output) and the check script `src/cli/tests/check_manifest.py` recomputes it after every milestone; any difference fails. The same script also runs `git diff --name-only HEAD` and fails when a tracked file other than `src/dbg/console.cpp`, `cmake.toml`, `CMakeLists.txt`, `src/tests/CMakeLists.txt` and the files below `src/cli/`, `src/tests/cli_target/` and `docs/` differs from `HEAD`; the milestone report (14) quotes `git diff --stat`, so a reviewer sees that the tracked core diff is that one file. `git diff` does not list untracked files, so the script also runs `git status --porcelain` and fails on any untracked path that is not below `.agents/`, `src/cli/`, `src/tests/cli_target/` or `docs/cli/`, or one of the four known untracked upstream trees (stray scratch files in the repository root are therefore caught).
2. **AC-2 Qt-free [M1].** While `x64dbg-cli.exe --json` runs, its loaded-module list contains no `Qt5*.dll` and no `x64gui.dll`.
3. **AC-3 Ready signal [M1].** In `--json` mode the first stdout line is `{"type":"hello",...}` and appears within 20 s of start. In text mode the first line is `@@READY x64dbg-cli 1 x64`.
4. **AC-4 Evaluate without a debuggee [M1].** Request `{"id":1,"op":"eval","args":{"expr":"1+2*3"}}` returns `ok:true` and `data.value == "0x0000000000000007"`.
5. **AC-5 Launch [M1].** `{"cmd":"init \"<abs path>\\cli_target.exe\", \"call\""}` (arg 1 = file, arg 2 = command line, as the native `init` documents) returns `ok:true`, `state.status == "paused"`, `state.pid != null`, `state.cip` non-null (paused at the system breakpoint) within the default timeout. An `init` of a nonexistent file returns `ok:false`, `error.code == "E_COMMAND_FAILED"`, and the message includes the core text "File does not exist!".
6. **AC-6 Pass-through and capture [M1].** `bp kernel32.Sleep`, `bplist`, `run`, `sti`, `log hello {rax}` execute after `init`; `output` contains the core's log text for exactly that command (including the first command after the hello line, which never carries init log text, 6.2 step 9); `findall <addr>,<pattern>` returns `tables[0]` with columns `Address`, `Disassembly` (non-empty, which needs `GUI_GET_DISASSEMBLY`); `labellist` after `lbl` returns the label in `tables`. Before any `init`, `bp kernel32.Sleep` returns `ok:false`, `error.code == "E_NOT_DEBUGGING"` (the core refuses debug-only commands, `command.cpp:351`). After `init`, `bp` without an argument returns `ok:false`, `E_COMMAND_FAILED`, with `error.message` containing `Not enough arguments` (the core prints it on the HTML channel, 7.1), and the `output` of the next response does not contain that text.
7. **AC-7 Breakpoint wait [M1].** After `bp` on a function the debuggee calls, `run` (F0) returns `ok:true`, `state.status == "paused"`, `wait.reason == "paused"`, `stop.reason == "breakpoint"` and an event `breakpoint_hit` with the breakpoint address, within the default timeout. A conditional breakpoint whose condition is false does not pause, and a later `pause` yields `stop.reason == "pause"` (7.5 step 1b): target mode `loop` (it calls `Sleep(10)` forever), `bp kernelbase.Sleep` plus `bpcond kernelbase.Sleep,0` (U42), `run` pending, `pause` sent 100 ms later, repeated 20 times; every `run` response has `stop.reason == "pause"`, and the harness first checks that `breakpoint_hit` events arrive during the wait, so the scenario really contains the stale hits. `sti`, `sto` and `rtr` end with `stop.reason == "step"`, and an access violation of the debuggee ends with `stop.reason == "exception"` and `stop.exception.code == "0x00000000c0000005"`. For `sti`/`sto` and the exception the `stepped` / `exception` event is in the response of the request that caused the stop, in each of 100 repetitions (these events are raised after the `paused` message, 3.6; T3a, T10). `rtr` raises no cause event (`cbRtrFinalStep`, 3.6); its `step` comes from the finisher refinement (7.5 step 5b), its response contains no `stepped` event, and it is not delayed by the trailing-cause wait (median `wait.elapsed_ms` of 50 `rtr` repetitions below `trail_ms`). `rtu` at the system breakpoint of the `call` mode ends with `stop.reason == "run_to_user"` (U41) and `TraceIntoConditional 1` (stops after the first step, `docs/commands/tracing/TraceIntoConditional.md`) with `"trace_end"`. A software breakpoint, a hardware breakpoint and an exception breakpoint (`SetExceptionBPX 0xc0000005,first` on the `except` target; `stop.bp` is the exception code and `stop.exception.code` equals it) each give `stop.reason == "breakpoint"`.
8. **AC-8 Timeout [M1].** With the debuggee in an infinite loop (F0), `{"cmd":"run","timeout_ms":500}` returns within 500 ms + 1 s with `wait.timed_out == true`, `state.status == "running"`; the debuggee keeps running (`on_timeout` default `keep`). Text-mode twin: the stdin line `!native --timeout_ms 500 -- run` ends with an `@@END <id> ok state=running ... wait=timeout` line within the same bound.
9. **AC-9 Pause during a wait [M1].** While a `run` wait is pending (debuggee in `loop` mode), a second request `{"id":"p","cmd":"pause"}` is answered by the Control thread immediately: its response has `ok:true`, `wait.reason == "paused"`, `state.status == "paused"`. The first request's response (own `id`) has `wait.reason == "paused"`, `state.status == "paused"`, `stop.reason == "pause"` and carries the events. Both responses are delivered, in either order, each with its own `id`; neither response contains the other's events.
10. **AC-10 Interrupt a wait [M1].** With a pending `run` on the `loop` target, `{"op":"interrupt"}` ends the wait: the `run` response has `wait.reason == "interrupted"`, `state.status == "running"`; the debuggee keeps running.
11. **AC-11 Exit [M1].** `run` on a debuggee that exits returns `state.status == "stopped"`, `state.exit_code` equal to the real exit code (7 for `call` mode), and an event `process_exited`. A following `init` starts a new session.
12. **AC-12 No false waits [M1].** Within 1 s and with `wait.waited == false`: `sti 0` on a paused debuggee gives `wait.reason == "not_resumed"`; `sti 0` and `erun` on a debuggee that is already running give `wait.reason == "already_running"`; `skip` on a paused debuggee gives `wait.waited == false` with `wait.reason == "none"` by default (class Other, 7.4) and with `wait.reason == "not_resumed"` for `{"cmd":"skip","wait":"always"}` (with `always` the reason is `not_resumed`; on a running debuggee `skip` is refused by the running guard). **Running guard (7.4):** on the `loop` target after `{"cmd":"run","wait":"never"}`, each of `sti`, `sto`, `rtr 5`, `skip`, `loadlib x.dll` and `run <address inside the loop>` answers `ok:false`, `error.code == "E_RUNNING"` within 1 s and the core is not called (no new breakpoint in `bplist`, no core log line of the command); the next `pause` answers `paused` within 2 s with `stop.reason == "pause"` and without the `pause_retry` warning; `sti 0` and `erun` on the running debuggee still answer `already_running`.
13. **AC-13 Structured views [M2].** Each of `!status !regs !dis !mem !memmap !stack !callstack !bps !threads !modules !sym !eval !process` returns `ok:true` with JSON matching the schema files of section 9.6 on a paused debuggee, and the values agree with cross-checks: `!regs` `rip` equals `!eval rip`; the first `!dis` row `text` equals the output of `log "{dis.text(rip)}"` (string expressions are formatted by `stringformat.cpp`, `dis.text` is `distext` in `exprfunc.cpp:408`), and so does every row of a listing that contains an instruction longer than 63 characters (the harness writes the bytes of an AVX-512 instruction with masking and a memory operand into an allocated page, asserts `len(text) > 63` first so that a wrong byte constant fails loudly instead of passing vacuously, U36); `!mem rsp -n 32` bytes equal `DbgMemRead`; `!memmap` page count equals `DbgMemMap` count; `!bps` lists every breakpoint printed by `bplist`. Near the end of readable memory the rows are still decoded: in a one-page `alloc` area filled with `nop` and ending in `c3` at offset `0xfff`, `!dis` returns every instruction down to `ret` without `truncated_reason`, and the `findall` table shows `ret` for the last address (T43).
14. **AC-14 Live disassembly [M2].** After each of `sti`, `sto`, `rtr`, `{"op":"dis"}` without address returns instructions starting at the new `cip` with `is_cip:true` on the first row.
15. **AC-15 State guards [M2].** `!regs` and `!stack` without `addr` on a running debuggee return `ok:false`, `error.code == "E_RUNNING"`; on no session they return `E_NOT_DEBUGGING`. `!mem`, `!dis <addr>` and `!stack --addr 0x<absolute address>` on a running debuggee work and carry `live:true`; for `!stack --addr` the data has `csp:null`, `cbp:null`.
16. **AC-16 Remaining views and parity [M3].** Every distinct `cli` target (a structured op or a native command) named by a row of `docs/cli/parity-matrix.csv` whose status is not `Gap` or `UI` is exercised once by T27 (rows that share a target share the test; the unit is defined in 11.5): ops with a schema check, natives with a line of `src/cli/tests/native_smoke.csv`. `src/cli/tests/check_matrix.py` parses every `*.ui` file below `src/gui/Src` for `<action name=...>` ids (the 103 ids of `MainWindow.ui` unprefixed, the others as `<ui base name>:<id>`; today `CPUWidget:actionGoto` and `TraceWidget:actionGoto`), lists the class base names of `src/gui/Src/Gui`, `src/gui/Src/Tracer` and `src/gui/Src/BasicView`, scans every `*.cpp` and `*.h` below `src/gui/Src` (except `ThirdPartyLibs`) for context-menu labels (`scan_menus.py`), and fails when an action id or a class name is missing from `docs/cli/parity-matrix.csv`, when a backticked word of a non-`Gap`, non-`UI` row is not an op, a native command or alias of the binary (`commands` op), a wildcard or an entry of the documented prose list of the checker, when a native target has no line in `native_smoke.csv` or a line names no target, when the scan finds fewer than 575 labels, when a scanned class has no `menu` row or the label count in the class cell of its rows differs from the scan (rule M at class level, section 11), or when a gap id used by a row is not documented in `docs/cli/README.md`. An `action` row whose `cli` text does not contain the command (or an alias of it, plus a literal word argument such as `bak`) that `makeCommandAction` binds to that action also fails (rule N; 29 statements in `MainWindow.cpp`; rows with status `Gap` or `UI` are exempt). Rows with status `Gap` are documented in `docs/cli/README.md` with the reason. *Amendment made in M3 (iteration 2, `deviations.md` item 49): the label-by-label expansion of the `menu` rows from `docs/cli/parity-groups.csv` was not built; the `menu` rows stay grouped per class and rule M is enforced at class level (class covered, label count equal to the scan).*
17. **AC-17 One-shot and exit codes [M1].** `x64dbg-cli.exe --exec "!eval 1+1; !eval nosuchsymbol"` exits with code 1 after the second command (the second reports `E_BAD_ARG`); with `--keep-going` it runs all commands and still exits 1; success exits 0; a bad option exits 2; a failed core initialisation exits 3 (test: copy `x64dbg-cli.exe`, `x64bridge.dll` **and** the C runtime DLLs (`vcruntime140*.dll`, `msvcp140.dll` from `bin\x64`; the project links the dynamic CRT, so on a machine without the VC++ redistributable the loader would fail with 0xC0000135 instead of reaching exit code 3) to a temporary directory, leave out `x64dbg.dll`, and run the copy; the exe imports `x64bridge.dll` implicitly, so without that copy the Windows loader would fail with 0xC0000135 before `BridgeInit` is reached); a wait timeout in one-shot mode exits 4. Startup input errors exit 2 before the core is touched and print one message to stderr (6.2 steps 1 and 3): a missing or unreadable `--script` file, a `--userdir` that cannot be created, a bad `--attach` pid, a numeric option out of range. `x64dbg-cli.exe --json --exec "!eval 1+1; log hi"` prints the hello line and two JSON responses with the ids `s1` and `s2` and exits 0 (8.1); `x64dbg-cli.exe --exec "!eval 1+1" < NUL` (stdin at EOF) prints the response and exits 0 because one-shot mode never reads stdin.
18. **AC-18 Never hang [M1].** (a) stdin EOF during a running debuggee (a pending `run`): the wait ends at most `eof_wait_ms` (5 s) after the EOF with `wait.reason == "shutdown"` and its response is written, then the CLI stops the debuggee, saves, exits within 20 s with exit code 0, and no orphan `cli_target.exe` remains (the normal path takes about 1 s; the worst case with a stuck core thread is bounded by the 30 s watchdog of 6.5). (a2) stdin EOF arriving while the Reader is between two reads, 100 repetitions with the hidden option `--test-reader-delay 20` (a random 0-20 ms delay before each `ReadFile`): exit code 0 within 5 s every time. (a3) EOF is graceful: `{"cmd":"eval 1+2"}` and `{"cmd":"log x"}` written to the pipe with stdin closed at once give both responses and exit 0; three queued `sti` followed by EOF while paused give three responses; `--exec "!eval 1+1" < NUL` exits 0 with the response printed (one-shot mode never reads stdin). (b) A request line over 1 MiB gets `E_TOO_LONG` and the next request still works. (c) A native line over 1023 bytes gets `E_TOO_LONG` without reaching the core. (d) Barrier timeout produces a response with a `barrier_timeout` warning rather than blocking. (e) With the CLI started with `--stuck-ms 6000`, a command that blocks inside the core (`scriptcmd zzz .20000`: `scriptcmd` runs one command; a script file is run by `scriptexec`) and has `timeout_ms:1000` gets `E_TIMEOUT` with `error.detail.busy == true` and `limit_ms == 6000` when the core call has lasted `coreCallLimitMs = max(stuck_ms, effective timeout_ms + 5000)` = 6000 ms, counted from the start of the blocking core call (8.4); later requests queue and are answered after it ends. (e3) While that blocking core call lasts, `{"op":"status"}` is answered within 1 s with `ok:true` (the Control thread reads only host-cached values and the calls of rule L6, 9.2). (e2) Only time inside a core call counts, and the limit does not depend on how short the client's wait is. With `--stuck-ms 6000`: a `batch` with batch-level `timeout_ms:20000` and the elements `{"cmd":"run","on_timeout":"pause"}` and `{"cmd":"run"}` on the `loop` target (two legitimate waits of 20 s, about 40 s in total) is answered without `E_TIMEOUT`; `{"cmd":"zzz .4000; zzz .4000; zzz .4000","timeout_ms":1000}` (12 s in total, 4 s per segment against a limit of 6 s) is not cut; and when `{"cmd":"zzz .8000; log after","timeout_ms":1000}` is cut (8 s > 6 s), the remaining segment `log after` is not executed. With the default `--stuck-ms 35000` (a separate CLI process): `{"cmd":"zzz .8000","timeout_ms":1}`, `{"cmd":"zzz .8000","timeout_ms":0}` and an `init` of `cli_target.exe` with `timeout_ms:1` are answered normally (`ok:true`, no `E_TIMEOUT`, no `late_result` event). A CLI started with `--timeout 0` answers `zzz .8000` normally. (f) A parent that never reads stdout does not freeze the CLI: after the parent closes stdin the CLI exits with code 70 within 35 s (the 2 s queue drain of 6.5, the 30 s watchdog as outer bound), and an outbound queue above 64 MiB ends in the fatal `E_OUTPUT_STALLED` (T38). (g) A crash inside the CLI process (SEH exception, CRT invalid-parameter, `abort()`) ends with one `fatal` line and exit code 70 within 5 s (T44).
19. **AC-19 Protocol hygiene [M1].** In a 200-command transcript every stdout line in `--json` mode parses as JSON, is valid UTF-8, contains no ESC (0x1b) byte; in text mode every response is one contiguous block ending with exactly one `@@END` line, even when a second response or an event is produced concurrently (a `pause` sent during a 200-line `findall` response); no stdout byte is produced by anything other than the protocol writer, verified by a debuggee that prints and a stray print injected under test (section 6.1).
20. **AC-20 Concurrency [M1].** 500 sequential pass-through commands interleaved with 20 pause/run cycles under an event-heavy debuggee (threads creating/exiting) complete with no deadlock, no out-of-order/duplicate `id`, and every response satisfies the testable consistency rule: `state.status == "paused"` implies `!DbgIsRunning()` at build time; `state.status == "running"` implies `DbgIsRunning()` or a `paused_state_unconfirmed` / `core_run_lock_held` warning in the same response (the transient states of 7.2 and AC-35 are the only exceptions).
21. **AC-21 Relative paths [M1].** With the CLI started from a directory containing `cli_target.exe`, `init cli_target.exe` and `--script rel.txt` resolve relative to the caller's current directory, not to `bin\x64`.
22. **AC-22 Prompts [M1].** `msgyn "continue?"` with the default policy sets `$RESULT` to 0 and an event `prompt` is recorded; with `--msgyn yes` it sets 1 (readable with `vars:["$result"]`). No dialog or blocking occurs. The script-timeout question ("The script has been running for a while...") is answered "continue" regardless of `--msgyn` (T14).
23. **AC-23 GUI regression [M1].** `x64dbg.exe` still builds, and a subset of the existing headless regression tests (`python src/tests/run.py` for at least `commandparser`, `cmdline_init`, `guard_page`) still passes after the `src/dbg/console.cpp` change (section 7.3).
24. **AC-24 Docs [M3].** `docs/cli/README.md` exists with the sections in FR-8 and contains at least three real transcripts produced by the implementation (stored under `.agents/tasks/cli/transcripts/`).
25. **AC-25 Self-test [M1].** `x64dbg-cli.exe --selftest` runs the pure unit tests (JSON, tokenizer, `;` splitter, hex/UTF-8 helpers, HTML stripper, barrier-marker splitter (both channels), command escaping, canonical-name resolver, native-line builders with rule N, option parser, the `!native` line parser (verbatim tail with quotes, backslashes and `;`; missing `--`; unknown key; empty tail), the startup value validation of 6.2 step 1 (numeric ranges, absolute paths, script decoding with BOM and invalid UTF-8), the line handling of 7.4 against a fake core that records the exact strings passed to `DbgCmdExecDirect` (the segment `$sti` arrives as ` $sti` with one leading space; `$$sti` expands once and arrives as ` $sti`; `log a; $sti` passes ` log a` and then ` $sti`, which the fake core fails; `set $v,1; $w=2` passes both segments; a 1023-byte segment is accepted and passes 1024 bytes, a 1024-byte segment is `E_TOO_LONG` and the fake core is not called; a fake `StringFormatInline` that fills its 65536-byte buffer gives `E_TOO_LONG` with no core call; `log x; $restartadmin` passes the refusal list, `log x; restartadmin` is refused with no core call), the target-argument builder `cli::joinTargetArgs` (`a b` -> `"a b"`, `c` -> `c`, empty -> `""`, `x"y` -> `"x\"y"`, a value with a space that ends in a backslash run gets that run doubled before the closing quote), the `vars` name rule (`$result` accepted, `result` rejected), the stuck-clock rule of 8.4 with a fake clock (a chain, a batch or a cv wait never fires; one long core call fires once and drops the rest), pause-reason attribution including the trailing-cause sequences and the trailing-cause wait with a fake clock, the tail path of the disassembly row helper with a fake memory reader) without loading the core and exits 0.
26. **AC-26 Attach/detach [M1].** The harness starts `cli_target.exe wait` itself; `{"cmd":"attach .<pid>"}` (the `.` prefix makes the pid decimal; a bare number is a hexadecimal expression) returns `ok:true`, `wait.reason == "running"` (attach does not pause the target, 3.6); `pause` gives `paused` within 8 s: the `wait` target sleeps in `Sleep(INFINITE)`, so the first `pause` cannot interrupt it and the CLI repeats the request after 2.2 s, which makes the core spawn a break-in thread (7.4); the response carries the warning `pause_retry`, while a `pause` on the `loop` target needs no retry and carries no such warning; `detach` gives `stopped` and the target process is still alive afterwards (U10, U21). `--attach <pid>` on the command line queues the same sequence.
27. **AC-27 Wait options [M1].** `on_timeout:"pause"` on a `loop` target ends `paused` with `wait.timed_out == true`; `on_timeout:"stop"` ends `stopped`; `wait:"never"` on `run` returns immediately with `state.status == "running"`; the text-mode twins are `!native --timeout_ms 500 --on_timeout pause -- run` (`@@END ... state=paused ... wait=timeout`), `!native --on_timeout stop --timeout_ms 500 -- run` (`state=stopped`) and `!native --wait never -- run` (`state=running`, no `wait=` reason other than `none`); `{"cmd":"attach .<pid>","wait":"always","timeout_ms":1500}` on a `wait`-mode target returns `wait.timed_out == true` with `state.status == "running"` (the attach does not pause, so the wait runs to its timeout). The same request issued while another session (the `loop` target) is live returns the same result: the `stopped` message that the attach sends for the old session does not end the wait (7.4, `always` for the Init and Attach classes).
28. **AC-28 Batch, vars, truncation, log [M1/M2].** `batch` (M2) with `stop_on_error:true` stops at the first failing element and returns the earlier results; `vars:["$result"]` returns the variable as a hex string (M1); `scriptexec <file>` of a script that the harness generates with 3000 lines `log "<100 characters>"` (about 300 KB of output; no single native command prints that much, a command line is capped at 1023 bytes) is cut at `max_output:4096` with `truncated:true` and `!log --from <next>` returns the remainder without loss (M1); `--log-file` mirrors the core log without barrier markers (M1).
29. **AC-29 Unsolicited events [M1].** With no request pending, a debuggee in `threads` mode that is running emits `{"type":"event"}` lines (text mode `@@EVENT`); each line parses; the sequence numbers are strictly increasing; none is repeated in a later response.
30. **AC-30 Overload [M1].** 300 pipelined `zzz .100` requests (`.` makes the argument decimal milliseconds; the core reads arguments as hexadecimal, so a bare `zzz 100` sleeps 256 ms, `docs/commands/misc/zzz.md`): requests beyond the 256-entry queue get `E_BUSY` immediately, all accepted requests are answered in order, the process stays responsive to `pause`.
31. **AC-31 Trace reader [M4].** After recording `call` mode with `StartTraceRecording` and `TraceIntoConditional 0`, `trace_open` reports an `instruction_count` equal to the number of traced steps, `trace_regs` at index 0 equals `!regs` captured at that point, and `trace_dis` rows equal `!dis` of the same code (section 14, M4).
32. **AC-32 Default two-stop sequence [M1].** Fixture F1. `init "<abs>\cli_target.exe", "call"` ends `paused` with `stop.reason == "system_breakpoint"`; `bp cli_target.marker_func`; the first `run` ends `paused` with `stop.reason == "breakpoint"` and `stop.bp` equal to the program entry (event `breakpoint_hit` named `entry breakpoint`); the second `run` ends `paused` at `marker_func` (`stop.bp` equal to its address); the third `run` ends `stopped` with exit code 7. `cli_target` has no TLS callbacks (the source must not use `thread_local` objects with dynamic initialisation, which make the CRT add a TLS callback; the harness asserts it by reading the PE TLS directory, `dumpbin /headers` or a small `pefile`-free parser, before the test), so the core plants no `TLS Callback n` stops (`debugger.cpp:1625-1638`) and the sequence is exactly the three stops above. The docs (FR-8) show this sequence.
33. **AC-33 Re-init over a live session [M1].** With a live paused session, `init "<abs>\cli_target.exe", "call"` (no `stop` before it) returns `ok:true`, `state.status == "paused"` with `state.pid` equal to the **new** process id, `stop.reason == "system_breakpoint"`, and never reports `stopped` for the old session (7.4 Init algorithm; repeated 50 times).
34. **AC-34 Resume without a state message [M2].** `loadlib winhttp.dll` (not loaded by `cli_target`, U32) on a paused target returns `wait.waited == true`, `wait.reason == "paused"`, `stop.reason == "loadlib"`, and `$result` (read with `vars:["$result"]`) is the loaded module base; `freelib` likewise with `stop.reason == "freelib"`.
35. **AC-35 Slow breakpoint command [M1].** A software breakpoint with `SetBreakpointCommand <addr>, "zzz .1500"` (command text sleeps 1.5 s while the core holds the run lock): `run` returns only after the command finished and the debuggee really paused or was resumed by the core; it never reports `paused` while the core is still inside the breakpoint command (7.2 truth check).
36. **AC-36 Event cap [M1].** With the `threads` debuggee and 5000 thread events pending, one `run` response carries at most `max_events` events (default 500), has the warning `events_truncated`, and `!events --since <events_next_seq>` returns the rest; if the ring wrapped, an `events_dropped` event with the lost count precedes the surviving events; no event is delivered twice (6.6).
37. **AC-37 Table ownership [M1].** `labellist; commentlist` in one request returns two tables in creation order with ids `n` and `n+1`; a second request returns only tables created after the first response; `!table --id n` pages a table that was already delivered (7.1a).
38. **AC-38 Numeric arguments [M2].** Wrapper ops hand numbers to the core in hexadecimal (rule N, 9.1): `!stepin --count 10` from a saved state ends at the same `cip` as ten `sti` natives from the same state; `!thread` with action `switch` and the decimal `tid` of a non-current thread (a tid above 9) makes that thread current (`state.tid` equals it); the builder self-tests of AC-25 yield `sti 0xa` and `switchthread 0x4d2`.
